# Комплексный аудит ошибок мессенджера

## 1. Проблемы с загрузкой сообщений

### 1.1. Фоллбэк через search API вместо get_history
В `src/api/mod.rs` (строки 1373-1439) реализован метод `get_messages_internal`, который:
- Пытается использовать `get_messages_via_session` (метод `messages` RPC)
- Если сессия недоступна или метод не работает, использует `get_messages_via_search` (строки 1563-1619)

**Проблема**: Метод `get_messages_via_search` выполняет 16 параллельных запросов к `search` API с разными поисковыми запросами (`"не", "на", "что", "он", "как", "мы", "вы", "но", "да", "то", "по", "из", "за", "ты", "от", "так", "все", "это", "ок", "привет"`). Это неэффективный фоллбэк, который:
1. Возвращает только сообщения, содержащие эти общие слова
2. Не гарантирует получение полного списка сообщений чата
3. Работает медленно из-за 16 параллельных запросов к search API

**Решение**: Использовать метод `get_history` через WebSocket (строки 630-656 в `WebSocketClient::get_messages`), который возвращает историю сообщений напрямую без поиска. В `HttpClient::get_messages_internal` необходимо:
- Приоритизировать `get_messages_via_session` (метод `messages` RPC)
- Улучшить кэширование сообщений с проверкой времени последнего обновления

### 1.2. Кэширование сообщений без валидации времени
В `src/api/mod.rs` (строки 1401-1439) кэш сообщений проверяется по файлу `messages_{chat_id}.json`, но:
- Нет проверки времени создания кэша
- Нет проверки актуальности сообщений (нет поля `last_message_id` или `updated_at`)
- При вызове `get_messages_fresh` с `skip_cache=true` кэш не используется, но при обычном вызове `get_messages` всегда используется кэш

**Решение**: Добавить в кэш метаданные с `last_message_id` и `cached_at`, и проверять их при загрузке.

### 1.3. Неполная поддержка WebSocket-уведомлений о новых сообщениях
В `src/api/mod.rs` (строки 383-471) обработка бинарных сообщений WS:
- Пытается распознать `ClientMessage.Plain` и `ServerMessage`
- Создает заглушки сообщений с `uuid::Uuid::new_v4().simple().to_string()` для `id` и `message_id`
- Не извлекает реальные `message_id`, `from_id`, `text` из `ServerMessageInfo`

**Решение**: Улучшить парсинг бинарных WS-сообщений для извлечения реальных полей `ChatId`, `MessageId`, `FromGuid`, `Text`.

## 2. Проблемы с отправкой сообщений

### 2.1. Отправка текстовых сообщений через WS или Session RPC
В `src/api/mod.rs`:
- `WebSocketClient::send_text_message` (строки 658-745) отправляет сообщения через WS с `ClientMessage.Plain`
- `HttpClient::send_message` (строки 1686-1713) использует `session_rpc_request("send_message", ...)`

**Проблема**: Метод `send_message` через RPC требует сессии (Passport cookies). Если сессия отсутствует или CSRF токен устарел, отправка не работает. Метод `send_text_message` через WS может не получать подтверждение от сервера о успешной отправке.

**Решение**: 
- Улучшить обработку CSRF токенов с автоматическим обновлением
- Добавить обработку ошибок отправки через WS (ошибки в `add_reaction`, `send_thread_message_ws` и т.д.)

### 2.2. Отправка файлов и вложений
В `chat_view.rs` (строки 662-705) метод `handle_attach`:
- Открывает диалог выбора файла
- Сжимает изображения (макс. 1920x1080, JPEG)
- Вызывает `on_attach(chat_id, bytes, filename)`

**Проблема**: В `api/mod.rs` метод `upload_file` (строки 1716-1753) использует `FILE_PUBLIC_HOST` и `chat_id` в URL для загрузки файла:
```rust
let upload_url = format!(
    "{}/media_upload/{}/{}?{}",
    config::FILE_PUBLIC_HOST,
    chat_id,
    filename,
    uuid::Uuid::new_v4()
);
```
Но Yandex Messenger API требует сначала получить временный URL загрузки через RPC `media_upload` или `upload_file`, а не отправлять файл напрямую по `chat_id/filename`.

**Решение**: Использовать правильный эндпоинт для загрузки файлов через RPC `media_upload` или получить `fileId` через `upload_file` RPC перед отправкой сообщения с вложением.

### 2.3. Отправка голосовых сообщений
В `api/mod.rs` (строки 1796-1843) метод `upload_voice_message` отправляет данные через `POST {base_url}/api/upload_voice` с параметрами `chatId`, `duration`, `waveform`.

**Проблема**: Формат запроса может не соответствовать ожиданиям сервера. Yandex Messenger требует:
- Правильный `Content-Type: audio/webm;codecs=opus`
- Правильную структуру `waveform` (массив `f32`)
- Подтверждение от сервера о загрузке голосового сообщения

## 3. Проблемы с интерфейсом и дизайном

### 3.1. CSS-переменные и стили
В `src/ui/theme.css`:
- Используется палитра Yandex Messenger (темная тема)
- Есть стили для `bubble-received`, `bubble-sent`, `message-bubble`
- Есть стили для `typing-dots`, `online-dot`, `unread-badge`

**Проблема**: 
- В `theme.css` есть неиспользуемые или конфликтующие CSS-классы (например, `@define-color bg_elevated` используется, но не определен в начале файла)
- В `chat_view.rs` (строки 1163-1167) добавляются CSS-классы `bubble-sent`, `bubble-received`, `message-bubble`, `bot-message`, но в `theme.css` классы определены как `.bubble-sent`, `.bubble-received`, `.message-bubble`, `.bot-message` - это соответствует, но есть проблема с `bot-message` стилями (строки 1805-1822 в `theme.css` используют `border-left: 3px solid #6366F1;`, но в `chat_view.rs` добавляется класс `bot-message` через `bubble.add_css_class("bot-message")`.

### 3.2. Обработка поиска по сообщениям
В `chat_view.rs` (строки 1140-1149):
```rust
let display_text = if !query.is_empty() {
    let escaped_query = glib::markup_escape_text(&query).to_string();
    let re = regex::RegexBuilder::new(&regex::escape(&escaped_query))
        .case_insensitive(true)
        .build()
        .unwrap();
    re.replace_all(&formatted_text, "<span background='yellow'>$0</span>").to_string()
} else {
    formatted_text
};
```

**Проблема**: 
- Использование `background='yellow'` не соответствует темной теме (желтый фон на темном фоне плохо читается)
- Нет подсветки совпадений в заголовках чатов или превью сообщений

**Решение**: Заменить `background='yellow'` на `background='rgba(255, 204, 0, 0.3)'` или использовать акцентный цвет Yandex (например, `#ffdc60`).

### 3.3. Состояния загрузки и скелетоны
В `theme.css` (строки 1274-1350) определены анимации `skeleton-loading`, `message-fade-in`, `pulse`, `spinner`, `pop-in`.

**Проблема**: 
- В `chat_view.rs` нет использования скелетон-загрузки при загрузке сообщений
- В `chat_list.rs` нет индикаторов загрузки при получении списка чатов

## 4. Проблемы с WebSocket-соединением

### 4.1. Автоматическое переподключение
В `src/api/mod.rs` метод `connect` (строки 234-264) реализует цикл переподключения с экспоненциальной задержкой (от 1с до 32с).

**Проблема**: 
- Метод `do_connect` (строки 267-490) создает новое WS-соединение, но не закрывает старое перед новым
- Метод `force_reconnect` (строки 551-560) просто сбрасывает `tx` канал и устанавливает состояние `Disconnected`, но не закрывает активное WS-соединение явно

**Решение**: Добавить явное закрытие WS-соединения при переподключении через `ws_stream.close(None).await`.

### 4.2. Обработка ping/pong
В `src/api/mod.rs` (строки 324-345) write-loop отправляет `Message::Ping(vec![].into())` каждые `WS_HEARTBEAT_INTERVAL` секунд.

**Проблема**: В read-loop (строки 348-479) обработка `Message::Text(text)` с `"operation":"pong"` отправляет ответ, но бинарные ping/pong сообщения не обрабатываются явно.

## 5. Проблемы с аутентификацией и сессиями

### 5.1. Загрузка сессии из `session.json`
В `src/api/mod.rs` (строки 872-919) метод `load_session_cookies` загружает сессию из `~/.config/yandex-messenger-native/session.json`.

**Проблема**: 
- Если сессия устарела (старше 30 дней), она отбрасывается, но приложение не предлагает пользователю выполнить повторную аутентификацию
- CSRF токен обновляется только при ошибке `bad_csrf_token`, но не при других ошибках аутентификации

**Решение**: Добавить явный флаг `is_session_valid` в `AuthManager` и показывать диалог аутентификации при устаревшей сессии.

### 5.2. OAuth токен vs Session cookies
В `HttpClient` есть два механизма:
- `token` - OAuth токен для RPC запросов
- `session_cookies` - Passport cookies для методов `messages`, `send_message`

**Проблема**: Метод `send_message` (строки 1686-1713) использует `session_rpc_request("send_message", ...)`, но если сессия отсутствует, отправка не работает. Метод `send_text_message` в `WebSocketClient` использует WS-отправку, но не гарантирует доставку.

## 6. Рекомендации по улучшению

### 6.1. Приоритет загрузки сообщений
1. Использовать `get_history` через WebSocket (метод `get_history` с `chatId`, `limit`)
2. Фоллбэк на `messages` RPC с сессией
3. Фоллбэк на `search` API только если первые два не работают

### 6.2. Улучшение отправки сообщений
1. Унифицировать отправку сообщений через WS или RPC с правильной обработкой ошибок
2. Добавить поддержку `reply_to`, `edit`, `schedule` в отправку сообщений
3. Улучшить загрузку файлов через правильный эндпоинт `media_upload`

### 6.3. Улучшение интерфейса
1. Исправить подсветку поиска на темную тему (использовать `rgba(255, 204, 0, 0.3)`)
2. Добавить скелетон-загрузки при получении чатов и сообщений
3. Улучшить обработку состояний отправки/доставки сообщений

### 6.4. Улучшение WebSocket-соединения
1. Явно закрывать старые WS-соединения при переподключении
2. Улучшить парсинг бинарных WS-сообщений для извлечения реальных ID сообщений
3. Добавить обработку ошибок WS-сообщений с логированием
